# Research: пакет релізу погодженого UX

Дата: 2026-09-30. Статус: власник схвалив реалізацію та випуск; реалізовано локально, реліз ще не виконано. Поточні докази та залишкові кроки: [статус релізу](research-ux-release-status.md).

Власник погодив напрям макета й попросив реліз **без моків**. Джерело поведінки: [специфікація](research-ux-spec.md), включно з останньою правкою: повернення зліва в області сторінки, додавання інтерв'ю справа на одній горизонталі.

## Відмінності, зафіксовані до реалізації

- SPA досі має п'ять розділів і починає з контексту, а не загального summary.
- Створення дослідження не підтримує старт із набору записів.
- `intelligence.js` вибирає одне джерело з перших трьох матеріалів для підготовки брифу.
- Серверний synthesis повертає `findings` із `text`/`source_ids`, без потрібних категорій та перевірених цитат.
- `/studies/:id/synthesis` повертає null після зміни контексту або джерел; попередній результат не залишається доступним.
- Запуск synthesis ручний; реальне автоматичне оновлення після готовності нового інтерв'ю ще потрібне.

## Пакет виконання

1. **Справжня продуктова поверхня.** Перенести погоджене компонування в React Research: Summary / Інтерв'ю / Бриф, повернення зліва та додавання справа, чотири блоки з розгортанням джерел, summary окремого інтерв'ю першим, транскрипт опційно. Приховати окремий план із основного флоу; зберегти існуючі дані задач і критерії в спільному брифі, без видалення старих записів.
2. **Створення й підтвердження.** Ручний бриф або завантаження кількох записів через чинні захищені endpoints. Підготовка брифу використовує весь обраний набір після транскрибації. Пропозицію переглядає та підтверджує власник. Стан чернетки/підтвердження зберігається на сервері, а не лише у вкладці. Старі дослідження сумісно залишаються доступними.
3. **Серверний аналіз.** Усі interview summary використовують спільний підтверджений контекст. Synthesis містить чотири категорії: інсайти, болі, що спрацювало, що не спрацювало. Джерела та цитати перевіряються за реальними матеріалами; відсутні докази не підміняються вигаданими прикладами. Старі outputs читаються сумісно й не отримують вигаданих категорій або цитат.
4. **Оновлення та повторне використання.** Готовність нових інтерв'ю запускає серверне оновлення aggregate з дедуплікацією jobs і чинними квотами. Зміна брифу зберігає попередній результат; лише «Оновити результати» запускає повторний аналіз за новими критеріями. Поточний незмінений результат не має постійної повторної генерації. Наявні транскрипти використовуються без повторної транскрибації; сумісні готові summary повторно не оплачуються.
5. **Перевірка й випуск.** Послідовні реалізація → перевірка → незалежне рев'ю. Потім реліз через чинний GitHub/Hostinger процес та перевірка доступності Research. Не видавати проходження тестових fixtures за перевірку реального AI.

## Правила для граничних ситуацій у цьому пакеті

- Помилка одного матеріалу не приховує попередні готові результати; повтор обробки стосується невдалого матеріалу.
- Автоматичне зведення виконується після завершення набору готових матеріалів, а не після кожного мерехтіння UI.
- Якщо бриф змінено, але власник ще не оновив результати, додавання матеріалів не створює суміш критеріїв: старий aggregate лишається позначеним як попередній, оновлення всього набору — вручну.
- Редагування транскрипту зберігає чинні механізми перевірки впливу; не приховувати реальну зміну джерела й не видавати старі докази за нові.
- Непогоджене видалення task comparison не входить у пакет; його дані зберігаються. Потрібні допоміжні дії можна лишити в додатковому доступі, без окремого обов'язкового кроку.

## Межі записів і збереження

Базовий commit: `fb272c81778acabceeb81121e5a54e07d1d5e763`. Наявні незакомічені зміни Research з попереднього проходу зберігаються; перед реалізацією буде збережено їхній diff і контрольні суми. Один writer загалом; агенти читання не змінюють файли й не делегують далі.

Основний scope: Research pages/components/hooks/utils/styles/locales; `server/modules/research/{router,intelligence,synthesis,validation}.js`, `server/modules/research/jobs/{router,worker}.js`, чинний summary/upload bridge та відповідні тести. Точні allowlists і передачі фіксуються перед кожним пакетом. `server/index.js` і спільні interview contracts резервуються окремо; `package-lock.json` не змінюється без потреби.

Якщо потрібне нове збережене поле стану брифу/набору, воно постачається SQL-міграцією в `server/migrations` із сумісними початковими значеннями для наявних досліджень. Застосування міграції до production не виконується приховано; перед цим потрібні перевірена міграція, конкретна ціль і власницька згода на цей запис.

Статичний макет, `research/dev/localPreview.js` та прапорець локальної фіктивної preview не використовуються продуктовими маршрутами. Немає демонстраційних інтерв'ю, фальшивих станів обробки або вигаданих даних у release build. Тестові fixtures допустимі лише у тестах; вони не стають джерелом продуктових результатів.

## Валідація

- Синтаксис/diff та сфокусовані unit/API/worker тести для змінених контрактів.
- Research build у зарезервований тимчасовий каталог, без кореневого `npm run build`, install або видалення client/admin output.
- UI тести навігації/збереження/порожніх станів/помилок; реальна автентифікація та API для ручного наскрізного перегляду, без увімкнення localPreview.
- Міграції перевіряються лише після окремої згоди на названу порожню disposable локальну БД. Seed/shared/production DB не використовуються як тестова база.
- Дорогі provider calls не запускаються як прихований smoke; перевірка конкретного реального інтерв'ю узгоджується за даними, середовищем і очікуваним запуском.
- Незалежний reviewer перевіряє докази та сумісність. Після релізу перевіряються workflow і живий Research, з чітким розділенням build success та перевірки AI-флоу.

## Звіт планування

1. Done: визначено реальні прогалини та сформовано пакет релізу без моків. Продуктові зміни ще не почалися.
2. Agents/models: головний Codex; read-only mapper `/root/research_map`, Luna/low. Другий mapper не запущений через ліміт runtime, серверну карту виконав головний агент.
3. Files: лише цей план; усі попередні зміни збережено.
4. Tests: read-only перевірка коду, контрактів та deploy workflow; поведінкові перевірки ще не запускалися.
5. Vault: no-op.
6. Remaining risks на момент планування: великий пакет зачіпає збережені результати, чергу AI та SQL зміни; потрібне схвалення плану до реалізації за orchestra guide.
7. Manual checks на момент планування: власнику погодити цей пакет; потім реалізація та випуск у межах дозволу. Власник згодом прямо погодив пакет: «Так, реалізовуй і випускай за цим планом».
