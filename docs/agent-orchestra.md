# Ручний оркестр агентів IteroJM

Власник вручну ставить продуктову задачу. Головний агент сам вирішує, чи працювати одному, чи делегувати за правилами нижче, і координує межі задачі, початковий стан, передачу файлів, приймання та фінальний звіт. Окреме схвалення кожного пакета виконавця не потрібне; велика або ризикована реалізація починається після схвалення плану власником. Немає hooks, розкладів чи автоматичного запуску. Правила продукту, дизайну, доменів і безпеки в `AGENTS.md` залишаються обов’язковими.

|---|---|---|---|

| `obsidian_keeper` / `obsidian-keeper.toml` | `gpt-6-luna` / `low` | workspace-write | 1–3 тис. токенів |

Це рекомендований обсяг додаткового task context, а не жорсткий token budget або розмір усього вікна. Передавайте мінімум релевантних фактів і посилання, без повних чатів. Для неіменованого subagent явно заданий default: Luna / low. Для іменованих ролей модель та effort визначає їхній файл. `code_mapper` у режимі `product_context_keeper` використовує той самий файл і Luna / low; режим змінює завдання, а не ресурсний профіль. Не обіцяйте override через аргумент spawn, якщо runtime не підтвердив, що він має пріоритет над файлом. Для ескалації головний агент створює новий явно налаштований обмежений пакет і підтверджений профіль; не припускає неявної зміни моделі існуючого агента.

Коли запускати ролі:

- `code_mapper`: невідомі точки входу, залежності або вплив зміни; повертає карту файлів, контракти й ризики без редагування. У режимі `product_context_keeper` звіряє продуктову мету й критерії приймання з мінімумом потрібних нотаток; суперечності передає головному агенту.
- `implementer`: є конкретні межі, критерії та передані файли; повертає реалізацію, стислий diff і результати перевірок.
- `test_writer`: потрібні нові поведінкові тести або окремий прохід перевірки; повертає покриті сценарії та фактичні pass/fail/skipped. Не писати тести, що лише повторюють реалізацію, для дрібних зворотних змін.
- `reviewer`: незалежне приймання середніх і ризикованих змін; повертає підтверджені findings або висновок із межами перевірки, без виправлень.
- `obsidian_keeper`: прийнята задача змінила довготривалі рішення чи знання; повертає лише потрібні оновлення нотаток і посилання. Для косметичних змін достатньо no-op.

Складна архітектура, невизначені ризики або суперечливий review виправдовують Astra / high. Перемикання головної сесії потрібно задати явно у підтримуваних налаштуваннях; цей документ сам effort не змінює. Не запускати сильнішу модель лише для пошуку файлів або переписування нотатки.

- Мала, зрозуміла задача низького ризику на 1–3 файли: головний агент або один implementer.
- Середня задача з визначеним scope: послідовно implementer → test_writer за потреби → незалежний reviewer → виправлення implementer → повторна перевірка змінених ділянок. Звичайні наявні перевірки може виконати implementer у своєму пакеті.
- Велика, багатомодульна, незрозуміла або високоризикова задача: спочатку план та схвалення власника перед записом.

Максимум два subagents одночасно, без урахування головного агента. Незалежні read-only дослідження стабільних файлів можна паралелити. Writer лише один загалом: головний агент теж writer; команди тестування з outputs та записи у vault отримують окрему послідовну передачу. Читачі не повинні перевіряти файли під час їхнього активного редагування. Після двох невдалих спроб агент зупиняється, повертає докази і просить ескалацію.

## Пакет задачі

Пакет заповнює головний агент до запуску. Абсолютні `write_files` — точний перелік дозволених вихідних файлів. `artifact_dirs` окремо дозволяє лише конкретні каталоги generated/test/build outputs, де назви файлів можуть визначатися під час виконання. Порожні обидва списки означають read-only; корінь продукту не може бути artifact directory. Приклад потребує заміни placeholders реальними шляхами й командами.

```yaml

mode: implementation # product_context_keeper можливий для code_mapper
objective: "Конкретний очікуваний результат"

  plan_approval: "Для великої/ризикованої реалізації — рішення власника; інакше n/a"
  write_files: [] # точні абсолютні шляхи вихідних файлів; без globs і папок
  artifact_dirs: [] # лише конкретні каталоги generated/test/build outputs
  exclusions: ["deployment", "migrations", "seeding", "production network"]

  - "Спостережуваний критерій завершення"
```

## Ledger володіння файлами

Головний агент веде ledger у task context перед кожною передачею, без вимоги додавати файл до repo. Один запис містить: task/phase, точні вихідні файли та каталоги outputs, baseline і pre-existing changes, поточного writer, read-only споживачів, час передачі, фінальний diff та статус released/active. Новий writer стартує тільки після released попереднього та перевірки актуального baseline.

`server/index.js`, `package-lock.json` та спільні контракти interview (структурований JSON, нормалізація transcript, system-state metadata й залежні UI/storage) потребують явної резервації. Невідомі залежні файли спочатку досліджують, потім головний агент уточнює пакет у межах дозволеної задачі; розширення продуктового scope погоджує власник. Заборонені записи поза allowlist, скасування чужих змін, ослаблення тестів, самостійні deployments, migrations, seeding і production network дії. Потреба в них повертається власнику для окремого рішення.

`sandbox_mode` і текстовий allowlist не забезпечують per-file OS enforcement. Дозволи батьківської сесії є верхньою межею; live overrides можуть мати пріоритет над defaults. Не вважайте write-доступ автоматичним схваленням scope.

## Приймання і перевірка

Reviewer незалежно читає scoped diff, acceptance та докази test_writer. Перевіряє регресії, граничні стани, доступ/ролі/workspace, помилки й доменні/security контракти. Findings містять severity, file/line, відтворення чи доказ; pre-existing проблеми відділяються від нових. Read-only reviewer не виправляє код і не запускає команди, що генерують outputs: необхідні executable checks запитує у test_writer. Головний агент організовує виправлення і reviewer повторно перевіряє змінені ділянки.

Звітуйте реальні команди, pass/fail/skipped, середовище і причину пропуску. Невелика перевірка TOML доводить синтаксис, але не завантаження Codex-профілів чи end-to-end роботу оркестру. Mock-pass не означає production ready. Для продукту вибирайте потрібні перевірки за ризиком і чинними правилами `AGENTS.md`.

Кореневий `npm run build` запускає install, завантажує Chromium і видаляє generated client/admin output — не рутинна перевірка. `research` є окремим workspace і пише build у `server/public/research`. Будь-який build/output-generating test потребує writer ownership і allowlist outputs. E2E seed пише БД; не запускати автоматично. Migration test можливий тільки з явним дозволом власника і названою порожньою disposable локальною БД; production/shared БД неприйнятна.

## Obsidian

Vault: `/Users/avrdnn/Desktop/iterojm/iterojm-obsidian`, сусідній каталог до Git-репозиторію; сам vault наразі не має Git. Keeper після приймання отримує тільки явно схвалені абсолютні `.md` шляхи; не `.obsidian`, інші vaults або довільні каталоги. Поточна батьківська workspace може включати vault, але нова repo-root сесія може потребувати точного vault path лише для keeper під дозволами батьківської сесії. Це не технічна vault-only ізоляція: workspace-write також залежить від робочої папки та live permissions. Не розширюйте writable roots усіх агентів. Якщо доступ відхилено, keeper повертає запропонований текст головному агенту.

Читати мінімум релевантних нотаток. Приблизно 46 наявних нотаток переважно з травня 2026, тому Research може бути застарілим: факти реалізації перевіряти в коді/тестах, пріоритети визначає намір власника. Не приймати старі нотатки автоматично. Масове оновлення vault — окрема задача.

Оновлювати наявне перед створенням нового. Маршрути: `01 Product` — продукт/намір, `02 Architecture` — структура/контракти, `03 Operations` — операції, `04 Decisions` — рішення й чому, `05 Workstreams` — стан роботи, `06 Maps` — зв’язки, `07 Runbooks` — перевірені процедури, `09 Open Questions.md` — невизначеність, `99 Changelog.md` — коротка прийнята зміна. Зберігати established frontmatter `type`, `status`, `tags`, `updated`; додавати `verified_at` і source links там, де це має сенс.

Одна корисна довготривала summary на прийняту задачу: факти, rationale, evidence, статус, дата, джерела. Розрізняти planned / implemented locally / verified / deployed. Не зберігати secrets, logs, transcripts або chat dumps. Косметична зміна може завершитися без vault запису.

## Обов’язковий фінальний звіт

Виконавець повертає стислий звіт за форматом пакета. Головний фінальний звіт завжди містить сім пунктів, навіть коли значення «не застосовується»:

1. **Done:** результат і відповідність acceptance.
2. **Agents/models:** фактичні ролі, моделі, effort; якщо не запускали — прямо вказати.
3. **Files:** точні змінені файли та pre-existing changes, які збережено.
4. **Tests:** реальні commands/pass/fail/skipped і межі доказів.
5. **Vault:** оновлені paths або no-op/недоступно з причиною.
6. **Remaining risks:** невирішене, припущення та неперевірені runtime аспекти.
7. **Manual checks:** конкретні залишкові кроки власника або «немає».
