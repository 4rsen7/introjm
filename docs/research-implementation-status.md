# Research: реалізований зріз і порядок запуску

Дата: 24 вересня 2026. Гілка: `codex/research-service-architecture`.

Це локально перевірена beta для роботи зі збереженими транскриптами. Вона ще
не розгорнута. Міграції виконувалися лише на синтетичній тестовій базі. Доступу
до production, реальних AI-викликів, розсилок або платежів під час реалізації
не було. Архітектурний план описує також наступні, ще не реалізовані етапи.

## Що вже працює

- Окремий React/Vite-застосунок `research/`, українська й англійська мови,
  адаптивний інтерфейс, вхід тим самим Supabase-акаунтом. У браузері піддомени
  мають окремі сесії; автоматичного SSO між ними немає.
- Окремий Research workspace, явний ідемпотентний bootstrap, доступ власника
  та учасників. Потрібен активний beta-доступ власника для запису/аналізу.
- Дослідження для продукту/фічі/зміни: назва, обов'язкова спільна ціль,
  необов'язковий бриф. Інтерв'ю належить одному дослідженню.
- Саммарі як основний результат; транскрипт на окремій вкладці, з редагуванням
  сегментів, мовця й часу. Збереження перевіряє версії; незбережені правки
  захищені під час переходів, виходу й зміни workspace.
- Спільні `SummaryService`, нормалізація й компонент показу результатів для
  IteroJM і Research. Старі промпти/пресети/merge-контракт збережені. Research
  явно обирає чинний `prototype_testing`, `replace_all` та додає ціль і бриф
  як контекст дослідження, окремо від свідчень респондента.
- Окрема збережена черга для саммарі й узагальнення. Повторний enqueue тих
  самих версій повертає наявне активне завдання. UI відновлює опитування після
  перезавантаження. Старий worker не може зберегти результат після втрати lease.
- Опціональні загальні висновки з актуальних саммарі та посиланнями на
  інтерв'ю-джерела. Усі source IDs перевіряються. Інструкція моделі вимагає
  зберігати розбіжності й не вигадувати частоти, цитати чи кількість учасників;
  це не є гарантією фактичної точності AI — потрібне дослідницьке рев'ю.
- Результат із застарілих джерел зберігається в історії job, але не замінює
  актуальне саммарі. Застаріле узагальнення не повертається як поточне.

## Ізоляція й сумісність

У `workspaces`, `plans`, `subscriptions` додано `product_key`; старі записи
отримують `iterojm`. Research використовує той самий сервер і базу, але окремі
workspace та серверні маршрути. Browser RLS забороняє прямий доступ до Research.

Після ввімкнення `PRODUCT_SCOPE_ENABLED` старі серверні запити спрямовуються
на service-only SQL views `iterojm_*`. Ці views обмежують і читання, і записи,
включно зі старими операціями за `user_id`, без фільтра workspace. Це захищає
Research-підписки від скасування старими адмінськими маршрутами. Дані користувача
в адмінці завантажуються явними запитами без залежності від FK embedding views.

`server/billing/entitlements.js` залишається джерелом чинного IteroJM billing.
Research beta поки використовує окремі `research_access_grants`: термін доступу,
`max_studies`, `max_interviews`, `max_analyses`. Усі створення/резервування
серіалізуються блокуванням grant власника в SQL. Ліміти спільні для його
Research-просторів, архівні записи й невдалі аналізи враховуються. Автоматичного
оновлення періоду або повернення beta-ліміту немає; це не платіжний ledger.

Режим із вимкненими прапорцями сумісний зі старою схемою. Після появи Research
даних `PRODUCT_SCOPE_ENABLED` вимикати не можна: startup відмовить, щоб старі
маршрути не відкрили ці дані. `RESEARCH_ENABLED` і `RESEARCH_JOBS_ENABLED`
можна вимикати окремо.

## Поточний API

Усі маршрути нижче мають префікс `/api/research` і вимагають Bearer token.
Відповідь: `{status: 'success', data}`; enqueue повертає HTTP 202 з job у `data`.

| Маршрут | Призначення |
| --- | --- |
| `GET /workspaces`, `POST /bootstrap` | Вибір/створення Research-простору |
| `GET /studies?workspace_id=…`, `POST /studies` | Список і створення дослідження |
| `GET/PATCH/DELETE /studies/:id` | Деталі, ціль/бриф, soft archive |
| `GET/POST /studies/:id/interviews` | Інтерв'ю дослідження |
| `GET/PATCH/DELETE /interviews/:id` | Деталі, транскрипт, soft archive |
| `POST /interviews/:id/summary-jobs` | Аналіз поточного транскрипту |
| `GET /interviews/:id/summary-job` | Останній job, включно з помилками |
| `POST /studies/:id/synthesis-jobs` | Узагальнення актуальних саммарі |
| `GET /studies/:id/synthesis-job` | Останній job узагальнення |
| `GET /studies/:id/synthesis` | Актуальне узагальнення або `null` |
| `GET /jobs/:id` | Доступний учаснику результат/стан job |

Списки обмежені 50 записами за замовчуванням, до 100 через `limit`. Наступна
сторінка: `before=<останній id>`; порядок UUID, не дата. PATCH дослідження
вимагає `revision`; PATCH інтерв'ю — `research_revision`, `transcript_revision`,
`summary_revision`. Службові summary/status/scope поля не приймаються з клієнта.

Стан job: `queued`, `running`, `completed`, `stale`, `failed`. Lease — 2 хвилини,
heartbeat — 30 секунд, максимум 3 спроби, пауза між ними 30/60 секунд. Worker
обробляє одне завдання одночасно; provider request має timeout 90 секунд і abort.
При падінні між AI-викликом і записом результату зовнішній виклик може повторитися.

## Порядок перевірки та ввімкнення

1. Зняти схему staging: колонки, тригери реєстрації, constraints, policies,
   grants, views та всі `SECURITY DEFINER` RPC. Репозиторій не містить повного
   знімка production. Невідомий RPC може обходити RLS — його треба перевірити.
2. Перевірити PostgreSQL 15+ і всі очікувані legacy-таблиці. Якщо існує одиночний
   unique index `workspaces.owner_id`, core migration навмисно зупиниться:
   потрібне окреме погоджене рішення щодо provisioning/унікальності.
3. На staging застосувати по порядку:
   `20260924_research_core.sql`, `20260924_research_legacy_views.sql`,
   `20260924_research_jobs.sql`. Це одноразові міграції, їх не слід повторно
   запускати вручну. Перевірити PostgREST schema reload та CRUD через `iterojm_*`.
4. Додати beta grant для тестового власника довіреною адміністративною операцією.
   Для першого пілоту залишити обмеження близькими до defaults: 20 досліджень,
   100 інтерв'ю, 20 аналізів. Форма керування grants в адмінці ще не реалізована.
5. Використати `server/.env.research.example` і `research/.env.example` як
   шаблони. Спочатку `PRODUCT_SCOPE_ENABLED=true`, потім `RESEARCH_ENABLED=true`.
   Зареєструвати Research origin і recovery URL у Supabase Auth redirect allowlist.
6. Зібрати `npm run build:research`. Артефакт — `server/public/research`;
   production server обирає його за `RESEARCH_ORIGIN`. DNS, TLS і завантаження
   цього артефакту ще потрібно налаштувати. Чинний deploy workflow не змінено.
7. Запустити окремий процес `npm run worker:research` з серверними ключами та
   `RESEARCH_JOBS_ENABLED=true`; цей самий прапорець потрібен API. Спочатку
   запускати **один worker**. Підтримку постійного процесу на хостингу ще слід
   перевірити; масштабування кількості workers потребує fairness/concurrency limits.
8. Перевірити staging owner/member/outsider, обидва продукти, повтор enqueue,
   перезапуск worker, редагування під час аналізу, password recovery і ліміти.
   Зіставити живий результат AI з контрольним набором вручну. Лише після цього
   планувати production-реліз.

Для локальної роботи: `npm run dev:research`, окремо `npm run worker:research`.
Тестові команди нижче не використовують живі credentials і не запускають worker
з реальним провайдером. Не використовувати існуючий seed/e2e проти production.

Відкат: вимкнути Research jobs/API/UI й зупинити worker. Зберегти міграції,
дані та `PRODUCT_SCOPE_ENABLED=true`. Не повертати старий сервер, що не знає
продуктової ізоляції, після створення Research workspace.

## Перевірено локально

- `npm run test:server`: 47 перевірок HTTP-доступу, SQL/RLS, квот, fencing,
  ревізій, timeout/abort, сумісності саммарі. PGlite виконує фактичні SQL-міграції
  на мінімальній синтетичній схемі; це не заміна Supabase/PostgREST staging.
- `npm run test:research-ui`: 9 сценаріїв входу/недоступності, пагінації, перегляду
  саммарі, редагування, конфлікту версій, навігації з незбереженими змінами,
  відновлення job та узагальнення. API/Auth замокані, зовнішню мережу заблоковано.
- Production-збірки Research і чинного client проходять. Admin Vite build
  проходить; оболонка Refine у sandbox намагається записати update-notifier
  поза workspace, тому саму збірку перевірено прямим Vite.
- Промпти чинних UA/EN пресетів звірено з хешами до виділення спільного модуля.
  Це підтверджує сумісність коду, а не незмінність відповідей зовнішньої моделі.
- Додано `.github/workflows/research-checks.yml` без secrets, live seed чи deploy.
  CI workflow ще не запускався на GitHub.

## Наступні етапи

Докладний порядок R0–R8, зміни даних/API/UI та критерії готовності:
[План завершення реалізації](research-remaining-implementation-plan.md).
Це план майбутніх робіт; статус реалізованої beta вище не змінюється.

1. Приватні source assets, upload/resume, перевірка медіа, перенесення чинної
   транскрипції у durable worker без зміни якості pipeline, retention/cleanup.
2. Підготовка брифу й сценарію з ШІ, явні задачі/критерії успіху, версіонування
   дизайну дослідження та прив'язка task IDs до секцій поточного саммарі.
3. Семантична оцінка впливу правок. Зараз лише whitespace не вважається
   суттєвою зміною; решта змін консервативно потребує перегляду. Немає прихованої
   автоматичної регенерації або AI-витрат після кожного збереження.
4. Матриця задач/респондентів, графіки з перевірюваними знаменниками,
   confidence/coverage, великі вибірки через поетапне узагальнення. Поточний
   synthesis передає вибірку за один виклик; навантажувальне масштабування ще
   не перевірене. Кількість саммарі не називається кількістю унікальних людей.
5. Research-розділ наявної адмінки, підтримка jobs і grants, запрошення,
   billing після бізнес-рішення, метрики черги, alerting і production rollout.

## Ресурси розробки

За побажанням власника — максимум один допоміжний агент одночасно, вузька
задача й короткий контекст. Реалізацію делегували `gpt-6-sol / medium`;
короткі подальші пошуки можна доручати `gpt-6-luna / low`. Інтеграція й перевірка
безпеки залишаються у головного агента. Це політика цієї роботи, а не зміна
глобальних налаштувань акаунта. Модель саммарі продукту не знижувалася.
